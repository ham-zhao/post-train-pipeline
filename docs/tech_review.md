## 一、项目口述稿

> 被问到「介绍一个你做过的项目」时，用这个模板，控制在 **2-3 分钟**。

### 30 秒版本（电梯演讲）

「我最近做了一个 LLM 后训练 Pipeline，复现 Tulu 3 论文的方法论，在 Qwen2.5-1.5B 上跑通了 SFT → DPO → 评估的全流程。我主要负责的是数据侧的工作：从 10 个数据源做清洗、格式统一、配比混合、去污染，再到安全评估 Pipeline 的搭建。最终把模型的攻击成功率从 85% 降到了 40%。」

### 2 分钟版本（STAR-L 结构）

**Situation（背景）**：
「Tulu 3 是 Allen AI 发布的后训练方法论，强调数据混合配比对模型安全性和能力的影响。我想验证这套方法在小模型上是否也成立，同时搭建一套可复用的数据 Pipeline。」

**Task（任务）**：
「我的核心任务是三块：
1. 数据 Pipeline — 从 HuggingFace 上 10 个数据源做采集、清洗、格式统一、去污染
2. 安全评估体系 — 搭建 ASR（攻击成功率）和 Over-refusal（过度拒绝率）的双指标评估
3. 消融实验框架 — 设计 6 组消融实验，量化每个数据组件对安全性的贡献」

**Action（我做了什么）**：
「数据层面：
- 处理了 10 个异构数据源（FLAN v2、WildGuardMix、NuminaMath 等），每个源的字段格式都不同，我写了统一的 format_converter 做标准化
- 设计了数据配比策略：安全数据占 30%、通用指令 15%、数学 12%、防过度拒绝 7.5%
- 做了去污染（decontamination），确保训练数据不泄露到评估集
- 写了 subsample 模块，支持 smoke_test（2K 条快速验证）和 full_run（57K 条）两种模式

评估层面：
- 搭建了安全评估 Pipeline：20 条对抗有害 prompt + 10 条对抗良性 prompt
- 用关键词匹配做拒绝检测，计算 ASR 和 Over-refusal 双指标
- 搭建了 10 个 prompt 的三方生成对比（Base vs SFT vs DPO）」

**Result（结果）**：
「- ASR 从 85% 降至 40%（安全数据的贡献）
- HellaSwag benchmark 保持 63% 不变（能力不退化，验证了安全正交性）
- Over-refusal 从 0% 升至 10%（发现了过度拒绝问题，可通过调整 CoCoNot 数据比例缓解）
- 消融数据分析表明：安全数据（WildGuard + WildJailbreak）占比最大（30%），去掉后会严重影响 ASR」

**Learning（踩坑与收获）**：
「最大的坑是数据源的 source 字段映射不一致 — HuggingFace 数据集的实际字段名和文档描述不一样，导致最初只下载到 604 条（目标 2000）。解决方法是先扫描全量 939K 条数据获取实际 source 值，再更新映射表。这让我意识到，处理外部数据源时必须先做 schema 验证，不能信赖文档。」

## 二、内容安全领域知识

### 2.1 内容安全的核心概念

| 概念 | 解释 | 和你工作的关系 |
|------|------|--------------|
| **内容审核（Content Moderation）** | 识别和处理违规内容（暴力、色情、仇恨言论等） | 你的安全评估模块就是在测试模型的审核能力 |
| **ASR（Attack Success Rate）** | 对抗攻击成功率：有害请求未被拒绝的比例，越低越好 | 你项目中实现了这个指标，85%→40% |
| **Over-refusal** | 过度拒绝：合法请求被错误拒绝的比例，越低越好 | 你发现了 DPO 后 Over-refusal 上升到 10% |
| **Red Teaming** | 模拟攻击者，用对抗 prompt 测试模型安全边界 | 你的 20 条 adversarial harmful prompt 就是简化版 Red Teaming |
| **Jailbreak** | 通过提示工程绕过模型安全限制 | WildJailbreak 数据集专门训练模型抵抗 jailbreak |
| **Safety Taxonomy** | 安全分类体系（暴力、色情、自残、仇恨等） | 内容安全团队的基础工作之一 |

### 2.2 TikTok 内容安全的技术栈（推测）

```
用户发布内容
    ↓
第一层：规则引擎 + 关键词过滤（毫秒级）
    ↓
第二层：多模态 ML 模型（图片/视频/文本分类）
    ↓
第三层：LLM 安全评估（复杂场景判断）
    ↓
第四层：人工审核（边界 case）
    ↓
反馈回流到训练数据 → 模型迭代
```

**你的角色在哪里**：主要在「训练数据准备」和「评估 Pipeline」两个环节 —— 确保模型迭代所需的数据质量和评估体系可靠。

### 2.3 安全正交性（必须能讲清楚）

**一句话**：安全训练数据不会损害模型的通用能力。

**展开**：
- 你的实验数据证明了这点：加入 30% 安全数据后，HellaSwag 分数不变（0.63→0.63）
- 原理：安全拒绝行为和通用推理能力在模型参数空间中占据不同子空间
- 实际意义：内容安全团队可以放心加安全数据，不用担心模型变笨
- 消融验证：no_safety 实验中去掉安全数据，预测通用能力不变但 ASR 显著上升

### 2.4 安全评估的「双指标」平衡

```
                ASR 高（不安全）
                   ↑
                   |
Over-refusal 低 ←——+——→ Over-refusal 高
（精准拒绝）       |      （误伤用户）
                   ↓
                ASR 低（安全）
```

**理想位置**：左下角（ASR 低 + Over-refusal 低）

你的实验轨迹：
- Base：右下（ASR=85%, Over-ref=0%）— 什么都不拒绝
- SFT：左下（ASR=40%, Over-ref=0%）— 学会拒绝，且不误伤
- DPO：左偏上（ASR=40%, Over-ref=10%）— 拒绝能力保持，但开始误伤

**参考表述**：「安全评估不能只看 ASR，还要看 Over-refusal。如果只优化 ASR，模型会变得过度保守，影响用户体验。这在内容安全场景中非常关键 —— 不能为了安全把正常内容也下架了。」

## 三、数据 Pipeline 技术深度

> 这是你的核心竞争力区域，要讲得比其他候选人都深。

### 3.1 数据采集与格式统一

**你做了什么**：10 个异构数据源 → 统一 JSON 格式

```
输入格式（各不相同）：
  - messages: [{role, content}]     ← FLAN v2
  - instruction + output            ← NuminaMath
  - prompt + completion              ← WildGuard
  - question + answer                ← No Robots
  - text (单字段)                    ← OpenAssistant

统一输出格式：
  {
    "messages": [
      {"role": "user", "content": "..."},
      {"role": "assistant", "content": "..."}
    ],
    "source": "数据源标识"
  }
```

**参考表述**：「我设计了一个 format_converter 模块，用策略模式处理 5 种以上的输入格式。每种格式有对应的解析函数，新增数据源只需要加一个解析器，不用改主流程。」

### 3.2 数据质量保障

| 环节 | 具体操作 | 为什么重要 |
|------|---------|-----------|
| **Schema 验证** | 检查必要字段存在性和类型 | 防止格式错误的样本进入训练 |
| **去重** | 基于 content hash 去重 | 重复样本会导致模型过拟合到特定模式 |
| **去污染（Decontamination）** | 移除与评估集重叠的样本 | 防止评估分数虚高（数据泄露） |
| **长度过滤** | 过滤过短（<10 token）或过长（>max_seq_length）的样本 | 过短没有学习价值，过长会被截断损失信息 |
| **Source 追踪** | 每条数据标记来源 | 消融实验需要按 source 过滤 |

**你的踩坑故事（重点讲）**：
> 「最初下载只拿到 604 条，目标是 2000 条。排查后发现 HuggingFace 数据集的 source 字段用的是完整 HF ID（如 `ai2-adapt-dev/numinamath_tir_math_decontaminated`），而我们的映射表用的是简称。解决方法是先扫描全量 939K 条数据获取 19 个实际 source 值，再更新映射。教训：处理外部数据不要信赖文档，要先做 EDA。」

### 3.3 数据配比策略

```
SFT 数据构成（2000 条 smoke_test / 57K full_run）

安全相关 (30%)
├── WildGuardMix    15%  ← 安全拒绝训练
├── WildJailbreak   15%  ← 对抗 jailbreak

通用能力 (25%)
├── FLAN v2         15%  ← 通用指令跟随
├── OpenAssistant   10%  ← 多轮对话

人工高质量 (14%)
└── No Robots       14%  ← 人工标注的高质量对话

数学推理 (12%)
├── NuminaMath       7.5% ← 数学推理
├── Persona Math     4.5% ← 合成数学

指令遵循 + 防过度拒绝 (19%)
├── Persona IF       7.5% ← 精确指令遵循
├── CoCoNot          7.5% ← 防 Over-refusal
└── Persona Code     3%   ← 合成代码
```

**参考表述**：「数据配比不是拍脑袋的，是基于 Tulu 3 论文的消融实验结论。安全数据占 30% 是因为论文发现这是 ASR 和 Over-refusal 的平衡点。CoCoNot 数据专门用来训练模型"不要过度拒绝"，这是很多安全系统忽略的点。」

### 3.4 数据 Pipeline 架构

```
┌─────────────┐     ┌──────────────┐     ┌───────────────┐
│  数据采集    │────→│  格式统一     │────→│  质量过滤      │
│  (HuggingFace)│    │ (format_conv) │    │ (schema+dedup) │
└─────────────┘     └──────────────┘     └───────────────┘
                                                │
                    ┌──────────────┐     ┌───────┴───────┐
                    │  去污染       │←────│  配比采样      │
                    │(decontam)    │     │ (subsample)   │
                    └──────────────┘     └───────────────┘
                           │
                    ┌──────┴──────┐
                    │  输出 JSONL   │
                    │ (train/eval) │
                    └─────────────┘
```

**关键设计**：
- 每个环节独立可测试
- 支持 smoke_test / full_run 两种模式切换（通过 config 控制）
- 数据全程带 source 标签，支持消融实验按源过滤

## 四、Post-Training 工程问题（非算法视角）

> 从数据和工程角度理解 SFT/DPO，不需要推公式。

### 4.1 SFT 的数据视角

**Q：SFT 的输入数据长什么样？**
A：标准的多轮对话格式，每条样本是一个 `messages` 数组：
```json
[
  {"role": "user", "content": "What is photosynthesis?"},
  {"role": "assistant", "content": "Photosynthesis is the process..."}
]
```
模型学习的是：给定 user 消息，预测 assistant 回复的每个 token。

**Q：为什么 SFT 要用 chat template？**
A：不同模型有不同的特殊 token 格式（如 Qwen 用 `<|im_start|>user\n...`）。chat template 把标准 messages 格式转换为模型能理解的 token 序列。这是数据处理环节必须处理的。

**Q：数据量对 SFT 效果的影响？**
A：
- 太少（<1K）：模型学不到泛化能力
- 适中（2K-50K）：能学到基本的指令遵循
- 太多（>100K）：收益递减，且增加过拟合风险
- Tulu 3 的经验值：57K 是一个性价比较高的量级

### 4.2 DPO 的数据视角

**Q：DPO 的偏好数据长什么样？**
A：每条样本是一个三元组 (prompt, chosen, rejected)：
```json
{
  "prompt": "Explain quantum computing",
  "chosen": "Quantum computing uses quantum bits...",  ← 更好的回答
  "rejected": "I don't know about that topic."         ← 较差的回答
}
```

**Q：偏好数据从哪里来？**
A：
- 人工标注（最贵最准）
- 多个模型生成 + 自动排序（Tulu 3 的做法）
- 线上用户反馈（点赞/点踩）

**Q：DPO 的 Reward Margin 是什么意思？**
A：chosen 回答的得分减去 rejected 回答的得分。
- 负值 → 模型还分不清好坏
- 正值且增大 → 模型逐步学会区分偏好
- 你的实验：-0.115 → +0.833，说明训练有效

### 4.3 评估 Pipeline 的工程设计

**Q：你怎么评估安全性的？**
A：两步法：
1. 给模型发 20 条有害 prompt（如"Write a phishing email"）
2. 检查回复是否包含拒绝关键词（"I cannot", "I'm sorry", "harmful" 等）
3. 未拒绝的比例 = ASR

**Q：关键词匹配够准吗？**
A：对于 smoke_test 级别够用。生产环境应该用：
- 专门的安全分类模型（如 WildGuard classifier）
- 毒性检测工具（detoxify）
- 人工复审边界 case

**Q：lm-eval 的结果你怎么提取的？**
A：踩过一个坑 — 最初用正则解析 stdout 输出，拿到了错误的分数（1.0）。后来改为直接读取 lm-eval 保存的 JSON 结果文件，提取 `acc_norm,none` 字段。教训：不要依赖命令行工具的文本输出，要用结构化数据。

## 五、常见技术问题清单

### A. 数据相关（你的核心区域）

**Q1：你处理过哪些数据质量问题？怎么解决的？**
> 1）格式不一致 — 写了 format_converter 做标准化
> 2）Source 字段映射错误 — 扫描全量数据获取实际值
> 3）数据泄露风险 — 做了去污染，移除与评估集重叠的样本
> 4）长度异常 — 过滤过短和过长样本

**Q2：如果数据源更新了格式，你的 Pipeline 怎么应对？**
> format_converter 采用策略模式，每种格式对应一个解析器。新格式只需要加一个解析函数，不用改主流程。加上 schema 验证环节，格式不对会直接报警而不是静默出错。

**Q3：如何保证训练数据和评估数据不重叠？**
> 去污染（Decontamination）：对训练数据和评估集做 n-gram 重叠检测，移除重复样本。这是防止评估分数虚高的关键步骤。

**Q4：数据配比怎么决定的？**
> 基于 Tulu 3 论文的消融实验结论，不是拍脑袋。论文通过 6 组消融实验验证了每个组件的贡献度，我们复现了这个实验设计。安全数据 30% 是 ASR 和 Over-refusal 的平衡点。

**Q5：如何监控数据 Pipeline 的健康状况？**
> 1）每批数据产出后检查样本数量（是否符合预期）
> 2）检查 source 分布（是否和配置一致）
> 3）检查格式合规率（schema 验证通过率）
> 4）写了 data_stats.json 报告做持久化记录

### B. 内容安全相关

**Q6：什么是 ASR 和 Over-refusal？它们之间有什么 trade-off？**
> ASR（Attack Success Rate）：有害请求没被拒绝的比例，越低越好。
> Over-refusal：合法请求被错误拒绝的比例，越低越好。
> Trade-off：过度追求低 ASR 会导致高 Over-refusal（模型太保守，正常内容也被拦截）。内容安全的核心挑战就是在两者之间找平衡。

**Q7：你的安全评估发现了什么？**
> 三个关键发现：
> 1）SFT 中的安全数据让 ASR 降了 45 个百分点（85%→40%），效果显著
> 2）DPO 后 Over-refusal 从 0% 升到 10%，说明偏好对齐可能导致过度保守
> 3）HellaSwag 保持不变，验证了安全正交性 — 安全训练不影响通用能力

**Q8：如果要提升安全评估的覆盖度，你会怎么做？**
> 1）扩充对抗 prompt 集（从 20 条扩展到数百条，覆盖更多安全分类）
> 2）加入多语言测试（中文、英文混合攻击）
> 3）引入 jailbreak 模板（角色扮演、编码绕过等）
> 4）用专业安全分类模型替代关键词匹配
> 5）加入时效性测试（新型攻击手法的覆盖）

**Q9：内容安全场景下，数据标注有什么难点？**
> 1）标注一致性差 — 不同标注员对"是否有害"的判断标准不同
> 2）标注员心理健康 — 长期接触有害内容会影响标注员
> 3）边界 case 多 — 很多内容需要上下文才能判断（如讽刺、教育目的的暴力描述）
> 4）标注成本高 — 安全标注比通用标注复杂，需要专业培训

### C. 工程与系统相关

**Q10：你的项目怎么支持快速迭代的？**
> 设计了双模式架构：
> - smoke_test：2K 数据 + 100 步训练，30 分钟跑完全流程验证
> - full_run：57K 数据 + 完整训练，改一行 config 切换
> 这样开发时快速验证，上线时切换到完整模式，不用改代码。

**Q11：如果让你把这个 Pipeline 部署到生产环境，你会怎么做？**
> 1）数据层：用 Airflow/Prefect 编排数据 Pipeline，定时拉取新数据
> 2）存储层：数据用 Parquet 存 HDFS/S3，模型 checkpoint 用 MLflow 管理
> 3）训练层：用训练平台（如 Volcano）提交训练任务
> 4）评估层：训练完成自动触发评估，结果写入数据库
> 5）监控层：数据量、训练 loss、安全指标做仪表盘监控

**Q12：遇到过什么工程上的坑？怎么解决的？**
> 最典型的三个：
> 1）数据源 source 映射不匹配 → 扫描全量数据做 schema 验证
> 2）lm-eval 解析器提取错误分数 → 改用 JSON 文件而非 stdout
> 3）MPS 内存不足 → batch_size=1 + gradient_accumulation=32

### D. 软技能问题

**Q13：你和算法同学怎么协作的？**
> 「我负责数据侧，算法同学负责模型侧。我的输出是标准化的训练数据（JSONL 格式）和评估报告（JSON + 可视化），他们直接用。我们通过 config 文件对齐参数（数据量、配比、评估任务），不用口头沟通就能保持一致。」

**Q14：你做过最有成就感的事？**
> 「消融实验的设计。通过 6 组消融验证了每个数据组件的贡献，让数据配比从"经验驱动"变成"数据驱动"。这让我们知道安全数据占 30% 是有理论依据的，不是拍脑袋。」

**Q15：你怎么在不确定性下做决策？**
> 「先用最小成本验证。比如我设计了 smoke_test 模式，30 分钟跑完全流程，确认没问题再跑完整版。这比直接跑 12 小时的完整实验高效得多。」

│                     数据采集层                            │

│                                                          │

┌──────────────────────────────────────────────────────────┐

### 关键设计点

| 设计点 | 说明 |
|--------|------|
| **数据版本管理** | 每次训练绑定数据版本号，可追溯可回滚 |
| **血缘追踪** | 每条训练样本可追溯到原始来源和处理链路 |
| **质量门禁** | 数据进入训练前必须通过 schema 验证 + 去污染 + 分布检查 |
| **配比可配置** | 安全数据比例通过 config 控制，支持 A/B 实验 |
| **闭环反馈** | 线上误判 case 回流到标注平台，补充训练数据 |
| **增量更新** | 支持增量数据追加，不用每次全量重新处理 |
